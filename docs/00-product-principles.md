# AI 电商自动运营系统：产品原则

## 1. 产品定位

本系统不是单点 AI 生图工具、AI 生视频工具或内容发布工具，而是一个围绕电商商品运营的自动化系统。

核心目标：

> 用户上传一个商品后，系统逐步把它变成能上架、能发布、能挂商品、能复用、能追踪效果的完整运营资产。

系统必须同时支持两种工作方式：

- 自动化流水线模式：上传商品资料后，系统自动生成成品、创建上架信息和发布任务。
- 手动工作台模式：用户可以单独使用图片、文案、视频、成品预览、发布、导出等功能处理具体环节。

这两个模式必须共存。MVP 可以先做半自动闭环，但架构必须为最终自动化保留能力。

## 2. 长期目标

最终系统应具备（能力层面，不限于页面数量）：

- 待办驱动的日常入口
- 商品运营台（单商品闭环）
- AI 图片 / 文案 / 视频生成（内嵌于运营台）
- 成品预览与发布
- 上架与发布中心
- 自动化流程编排
- 平台账号管理
- 库存联动
- 数据回流
- 异常处理和任务恢复
- 二级工具：全量任务监控、跨商品成品检索

## 3. 核心设计原则

### 待办驱动，而不是功能堆砌

用户每天打开系统，应先看到 **「需要你处理什么」**，而不是一排功能模块。

- 待办收件箱：待发布、生成失败、缺素材、库存异常
- 点击待办 → 直达对应 **商品运营台**，不经过中间跳转

### 商品是中心

所有图片、文案、视频、上架信息、发布任务、库存、数据和日志都必须绑定到商品。

### 生成能力是服务，不是前台模块

RunningHub 只作为底层 AI 图片和视频生成引擎。前台用户只看到：

- 生成主图 / 详情页图 / 卖点图 / 视频
- 预览成品
- 确认发布
- 重新生成

### 人工确认 = 预览后发布，不是审核流程

用户不需要独立的「审核中心」或「审核任务」。

正确链路：

```text
待办提示 / 进入商品运营台
→ AI 生成（页内完成）
→ 预览成品（页内完成）
→ 满意后点发布 / 导出
```

### MVP 要收敛，但底层不能短视

第一版可以不做完整自动发布和自动上架，但数据模型、状态机、任务系统和页面结构必须为这些能力预留位置。

## 4. 第一版闭环

```text
待办收件箱（发现待处理事项）
→ 商品运营台（单页）
  → 创建 / 选择商品
  → 一键补全或分项生成图片、文案、视频
  → 预览成品、编辑文案、设主图
  → 确认发布 / 创建上架草稿
→ 发布中心（全局查看与导出）
→ 库存校验
→ 记录操作日志
```

日常操作目标：**80% 场景不超过 2 次主导航切换**。

## 5. 后续升级方向

- 接入真实 RunningHub 图片/视频生成
- 接入文案生成模型
- 引入异步任务队列
- 接入对象存储
- 接入平台账号授权
- 发布素材包导出 / 半自动发布 / 自动发布 / 自动上架
- 自动化流程与待办联动（节点完成自动推待办）
- 完成数据回流和效果分析

## 6. 界面收敛（2026-05）

产品入口对齐 [09 核心平台工作流](./09-core-platform-workflow-design.md)：

- **保留**：工作台、运营台、发布、账号、库存
- **移除导航**：策略、编排、数据中心、全自动批量、独立任务/成品库页
- **原则**：半自动 = 在运营台按节点手操；复杂自动化待 M14 平台工作流页
